# Stress run: Bitsmith alone, with optimisation mods, inside the Arcadia modpack, and against Chisels & Bits

[English](#english) | [Français](#français)

---

## English

### Setup

- One machine: Ryzen 7 5700X3D, Radeon RX 7800 XT, 32 GB. Minecraft 1.21.1, NeoForge 21.1.259,
  1280x720, render distance 12, simulation distance 8, no frame cap, VSync off, Fancy graphics,
  smooth lighting. Same Java heap for the three runs (8 GB), plus an Arcadia run at 12 GB.
- Three configurations, the same scenes (`StressPlaytest`):
  - **alone**: Bitsmith and Spark (`./gradlew runClientStress`);
  - **opti**: plus Sodium, Lithium, ModernFix, FerriteCore, ImmediatelyFast and Entity Culling
    (`runClientStressOpti`);
  - **arcadia**: Bitsmith inside the 450 mods of the Arcadia Echoes Of Power V2 pack, with its
    configs, KubeJS scripts and resource packs, copied from its instance; shaders off, no starter
    kit (`runClientStressArcadia`, `-Pbitsmith.stress.xmx=12G` for the larger heap).
- Scene: the eight reference blocks of the bench (16 single bits carved with the chisel in each)
  cloned into **16,000 carved blocks** (40 x 10 x 40); a control scene of plain stone of the same
  size.
- Scenes, 10 s each: T1 static view; T2 carving storm (a click every 2 ticks, 100 strokes);
  T3 placement storm (60 boxes of 14,415 bits, one every 2 ticks); T4 chunks loading back in after
  a teleport far away; T5 flying over; T6 saving the world.
- **One run per configuration**: the figures are indications, not medians. Spark profiles (server
  during the storms, client during the flight) and heap summaries are saved to files in each run's
  `config/spark`, never uploaded. Java Flight Recorder recordings (`-Pbitsmith.stress.jfr=true`)
  were used to find where the time goes.

### Fixed during this run: freeze when carved chunks load back in

The first runs showed a **656 ms frame** when coming back to the 16,000 carved blocks (stone:
129 ms). A flight recording put 54 % of the render thread in reading carved blocks: every block
entity of every chunk received decoded its grid on the render thread, although the 16,000 blocks
hold 8 distinct grids. Saved grids are now decoded once and shared (`GridNbt`). Same scene, alone:

| T4, carved chunks loading back in | before | after | stone |
|---|---|---|---|
| worst frame | 656 ms | **80 ms** | 129 ms |
| 1 % low | 60 fps | **115 fps** | 127 fps |

### Reading

- **Alone and with optimisation mods**, 16,000 carved blocks keep the game above 100 fps in 1 %
  lows in every scene except the placement storm (71 and 97 fps). Coming back to a carved build is
  now as smooth as coming back to stone, or smoother. The optimisation mods lower memory by a third
  and help every scene.
- **The static view** of 16,000 carved blocks costs more than stone alone (580 vs 966 fps on
  average): carvings have many more faces. In Arcadia the two are equal (705 vs 706 fps): the pack's
  own cost dominates.
- **Arcadia at 8 GB is short of memory**: 7.7 GB of the 8 GB are in use after a collection, before
  any carving. The 2-second freezes on chunk reload happen with plain stone too (1787 ms) and go
  away with 12 GB (147 ms, carved and stone alike). They come from the heap, not from Bitsmith.
  This is a development run (unobfuscated classes, no launcher), so the pack may need less in
  CurseForge, where it is set to 6 GB; worth watching on a real install.
- **Carving inside Arcadia is slower** (1 % low 39 fps, server tick p95 11 ms). A flight recording
  of the storm finds Bitsmith in **0 % of the server thread samples** and 1.7 % of the render
  thread's: the time goes to the pack's other mods running every tick (Accessories, Curios, the
  Cosmetic Weapons procedures, Entity Culling, Sodium...). Bitsmith's own work per stroke stays
  under half a millisecond.
- **Saving** takes 1 to 1.7 s in Arcadia against 70 ms alone: the pack has nine dimensions and
  many mods saving data; Bitsmith's share is the same 16,000 block entities in all runs.

### Compared with Chisels & Bits

The same scenes with Chisels & Bits 21.1.33 instead of Bitsmith (`./gradlew runClientStressCnb`),
the eight references carved with its own iron chisel, then Bitsmith alone right after, in the same
session. The placement storm (T3) is left out: Chisels & Bits has no shape placement. Since this run,
the stress test waits until the game is playable again after building the scene (60 fps over a
second) and records how long that took. Bitsmith's own figures vary between runs on this machine
(T2 1 % low: 181 fps this afternoon, 71 fps here), so only large gaps mean something.

| Scene | Metric | Chisels & Bits | Bitsmith |
|---|---|---|---|
| Building the scene | playable again after | **81.2 s** | **1.0 s** |
| | server lag while cloning 16,000 blocks | 15.6 s behind | none |
| Memory | heap in use at rest | 3090 MB | 704 MB |
| At rest | server tick avg / p95 | 8.53 / 14.61 ms | 4.22 / 4.73 ms |
| T1 static view | fps avg / 1 % low | 204 / 5 | 840 / 256 |
| | worst frame | 499 ms | 5.8 ms |
| T2 carving storm | fps avg / 1 % low | 380 / 30 | 566 / 71 |
| | worst frame | 78.6 ms | 49.8 ms |
| T4 carved chunks back in | worst frame / 1 % low | **4249 ms** / 1 | **94 ms** / 62 |
| | server tick worst | 117.9 ms | 8.3 ms |
| T5 flying over | fps avg / 1 % low | 200 / 10 | 653 / 110 |
| | worst frame | 1213 ms | 27.5 ms |
| T6 save | world save | 135 ms | 138 ms |

The stone control of T4 is within render distance of the carved scene, so with Chisels & Bits it
also reloads the carved chunks (worst frame 4648 ms); it is left out of the table.

At 16,000 carved blocks, Chisels & Bits needs more than a minute to become playable after the scene
is built, holds four times the memory, doubles the server tick at rest, and freezes for over four
seconds each time the chunks come back. Bitsmith stays smooth in every scene; saving costs the same.


### Reproducing

```
./gradlew runClientStress
./gradlew runClientStressOpti
./gradlew runClientStressCnb                                    # the same scenes with Chisels & Bits
./gradlew runClientStressArcadia -Pbitsmith.stress.xmx=12G     # -Pbitsmith.arcadia=<instance folder>
./gradlew runClientStressArcadia -Pbitsmith.stress.jfr=true    # flight recordings of T2 and T4
```

Results are the `STRESS` lines of each run's `playtest-report.txt`. Do not type in the game window
during a run: it takes the focus, and key presses move the player.

### Lecture

- **Seul et avec les mods d'optimisation**, 16 000 blocs ciselés gardent le jeu au-dessus de
  100 fps en 1 % bas dans toutes les scènes sauf la tempête de poses (71 et 97 fps). Revenir vers une
  construction ciselée est maintenant aussi fluide que revenir vers de la pierre, voire plus. Les
  mods d'optimisation baissent la mémoire d'un tiers et aident chaque scène.
- **La vue fixe** de 16 000 blocs ciselés coûte plus que la pierre en mod seul (580 contre 966 fps
  en moyenne) : les sculptures ont beaucoup plus de faces. Dans Arcadia les deux sont égales (705
  contre 706 fps) : le coût propre du pack domine.
- **Arcadia à 8 Go manque de mémoire** : 7,7 des 8 Go sont utilisés après un ramasse-miettes, avant
  tout ciselage. Les blocages de 2 secondes au rechargement des chunks arrivent aussi avec de la
  simple pierre (1787 ms) et disparaissent avec 12 Go (147 ms, ciselé comme pierre). Ils viennent de
  la mémoire, pas de Bitsmith. C'est un run de développement (classes non obfusquées, pas de
  launcher), le pack peut donc demander moins dans CurseForge où il est réglé à 6 Go ; à surveiller
  sur une vraie installation.
- **Ciseler dans Arcadia est plus lent** (1 % bas 39 fps, p95 du tick serveur 11 ms). Un
  enregistrement de la tempête trouve Bitsmith dans **0 % des échantillons du thread serveur** et
  1,7 % de ceux du thread de rendu : le temps part dans les autres mods du pack qui tournent à chaque
  tick (Accessories, Curios, les procédures de Cosmetic Weapons, Entity Culling, Sodium...). Le
  travail propre de Bitsmith par coup reste sous la demi-milliseconde.
- **La sauvegarde** prend 1 à 1,7 s dans Arcadia contre 70 ms en mod seul : le pack a neuf
  dimensions et beaucoup de mods qui enregistrent des données ; la part de Bitsmith est la même,
  16 000 block entities, dans tous les runs.

### Comparaison avec Chisels & Bits

Les mêmes scènes avec Chisels & Bits 21.1.33 à la place de Bitsmith (`./gradlew runClientStressCnb`),
les huit références ciselées avec son propre ciseau en fer, puis Bitsmith seul juste après, dans la
même session. La tempête de poses (T3) est laissée de côté : Chisels & Bits n'a pas de pose de
formes. Depuis ce run, le test attend que le jeu redevienne jouable après la construction de la
scène (60 fps sur une seconde) et note le temps que ça a pris. Les chiffres de Bitsmith varient
d'un run à l'autre sur cette machine (1 % bas de T2 : 181 fps cet après-midi, 71 fps ici), seuls les
grands écarts ont donc un sens.

| Scène | Mesure | Chisels & Bits | Bitsmith |
|---|---|---|---|
| Construction de la scène | de nouveau jouable après | **81,2 s** | **1,0 s** |
| | retard du serveur en clonant 16 000 blocs | 15,6 s | aucun |
| Mémoire | heap utilisé au repos | 3090 Mo | 704 Mo |
| Au repos | tick serveur moy. / p95 | 8,53 / 14,61 ms | 4,22 / 4,73 ms |
| T1 vue fixe | fps moy. / 1 % bas | 204 / 5 | 840 / 256 |
| | pire image | 499 ms | 5,8 ms |
| T2 tempête de ciselage | fps moy. / 1 % bas | 380 / 30 | 566 / 71 |
| | pire image | 78,6 ms | 49,8 ms |
| T4 retour des chunks ciselés | pire image / 1 % bas | **4249 ms** / 1 | **94 ms** / 62 |
| | pire tick serveur | 117,9 ms | 8,3 ms |
| T5 survol | fps moy. / 1 % bas | 200 / 10 | 653 / 110 |
| | pire image | 1213 ms | 27,5 ms |
| T6 sauvegarde | sauvegarde du monde | 135 ms | 138 ms |

Le témoin de pierre de T4 est à portée de rendu de la scène ciselée : avec Chisels & Bits, il
recharge aussi les chunks ciselés (pire image 4648 ms) ; il est laissé hors du tableau.

À 16 000 blocs ciselés, Chisels & Bits met plus d'une minute à redevenir jouable une fois la scène
construite, occupe quatre fois plus de mémoire, double le tick serveur au repos et se fige plus de
quatre secondes à chaque retour des chunks. Bitsmith reste fluide dans toutes les scènes ; la
sauvegarde coûte la même chose.
